### The `settings.json` conflict and how it was resolved (plan D-H)

First native run: the real Claude CLI rewrites `~/.claude/settings.json` (same content, other key order and whitespace) while installing plugins. `chezmoi diff` was then not empty and a plain second `apply` stopped with
`.claude/settings.json has changed since chezmoi last wrote it?` / `could not open a new TTY` (exit 1). A draft of this test accepted that as `KNOWN` and continued with `--force`; that tested the workaround, not idempotence, and was removed.

Spike, `run_onchange_before_` for the Claude installer (real CLI, reverted afterwards):

| Scenario | Result |
| --- | --- |
| fresh `init --apply`, plain second apply | exit 0, empty diff |
| `accepted_sha` changed + `AI_WORKFLOW_UPGRADE=1` (no installs) | exit 0, empty diff |
| existing host, `minimal` -> `claude-extended` (14 installs) | **exit 1**: the CLI rewrote the file before chezmoi wrote it, and chezmoi already had a recorded hash; the next plain apply failed too |

Rejected for that third row. Adopted instead: the Claude installer (`.sh` and `.ps1`, still `run_onchange_after_`) saves the exact bytes and mode of `settings.json` before the first mutating CLI command and always restores them
(copy next to the file, then rename; a file the CLI created is removed; a failed restore or snapshot counts as `partial`). Verified:

- stub layer: `STUB_REWRITE_SETTINGS` makes the stub CLI rewrite/create the file on every mutating call; `test_claude_installer.sh` (l1-l7) covers restore of bytes and mode, restore after failing installs, removal of a created file, an impossible restore (-> `partial`, exit 0, no temp left), `ai_claude=false`; `test_fresh_home.sh` runs every cell with the rewriting stub and adds the profile-switch cell; 20 cells PASS. With the restore disabled these tests fail (checked once, reverted).
